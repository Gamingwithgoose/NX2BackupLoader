Suite 0.4 native SDK OS experiment

The console runs source/sdk_os.c on a libounce worker only after all six exact
Yoshi NSO hashes and relocations pass. The main game entrypoint and complete
SDK initialization are deliberately not part of this experiment.

The worker saves the SDK-owned TLR tail (0x180..0x1ff) and TPIDR_EL0, presents a
zero-initialized SDK tail, and calls the named SDK OS functions. It restores
both before any host runtime call. Kernel-maintained TLR fields are not restored
from stale copies. A nonzero preemption counter refuses entry; an imbalanced
counter/context-restoration fault keeps the worker out of host teardown while
the normal host thread ends the process. There are no calls to host logging,
allocation or libounce between SDK entry and restoration.

This is controlled execution in one existing process, not memory isolation or a
universal exception recovery mechanism. CPU faults and unexpected SDK behavior
can still terminate the process. The read-only kernel-call observation below
is from the emulated path, not enforced by a console syscall filter.

Reproduce PC integration test from this probe directory:
1. Follow STARTUP.txt to export verified images and capture native linker results.
2. Build tests/native_parity.c as described there. Run with an optional third
   argument to export our C-linked SDK image into the private scratch directory:
   native_parity.exe EXEFS_DIR SCRATCH SCRATCH
3. Build the normal probe via the repo's build.bat. In a devkitPro shell link the
   actual worker object into a small test ELF:
   aarch64-none-elf-gcc -nostdlib -shared -Wl,-T,fixture/module.ld -Wl,-Bsymbolic -Wl,-z,max-page-size=4096 build/sdk_os.o -o tests/sdk-os-worker.elf
4. Python needs unicorn 2.1.4. Run each case (normal, busy, bad-thread, tls-failure):
   python tests/emulate_sdk_worker.py SCRATCH --process-info-json tests/process-info-03.json --worker tests/sdk-os-worker.elf --case normal

The normal case executes the compiled worker and actual SDK functions, with a
nonzero host TLS sentinel. The worker must return with the sentinel and original
TPIDR_EL0 intact. It checks SDK thread identity, TLS state and mutex semantics.
The remaining cases inject a precondition failure or simulated bad callee result
and require context preservation without dereferencing an invalid thread object
or using an unallocated TLS slot.

The single-thread model handles LSE CAS without testing memory ordering/coherence,
uses synthetic worker ID/priority/handle and deterministic entropy, models PAC
returns without signature validation, and supplies observed process GetInfo
replies from the retained 0.3 capture. The simulated stack mapping is not a
captured console mapping. The normal path requested 21 GetInfo, two QueryMemory,
one GetThreadPriority and one GetThreadId calls. No service or storage request
was forwarded. The private SDK image is not included in this repository.

Captured cases are in sdk-worker-*.json. Hardware report received 2026-11-20 passed 152/152 checks, including SDK OS initialization, matching kernel thread ID, TLS read/write/release, mutex behavior, host TLS/TP restoration and all unmaps. See hardware-suite-04.txt. The earlier
0.3 hardware success (131/131) did not execute these SDK functions.
